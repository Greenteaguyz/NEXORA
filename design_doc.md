## Problem Statement

Build a first-year capstone project: **NEXORA**, a modern cyberpunk & indie downloadable-games marketplace inspired by itch.io. The grading panel evaluates auth, role-aware access, ownership checks, **CRUD**, and data flow. A 3-person team where one person (you) does the majority of coding, with 10 working days (~2 weeks) to ship.

## What Makes This Cool

The gated download flow. An anonymous user clicks "Download" and gets bounced to login, logs in, gets redirected back, and the download proceeds — with free vs paid branching, a purchase confirmation modal, library entry creation, and a real file download. Five distinct download-button states. It's a chain of auth, routing, data mutations, and UI state that feels like a real product.

## Constraints

- **Solo primary developer**, **10 working days (~2 weeks)** — this is the single timeframe used everywhere in this document; earlier drafts said "1–2 weeks" in one place and "10-day deadline" in another, which is the same window stated two different ways. Treat them as identical.
- **First-year capstone** — graded on demonstrated competencies, working demo, and ability to explain decisions
- **Frontend-only** — no backend, mock data with IndexedDB persistence
- **Angular 17+** — standalone components, signals, new control flow (`@if`, `@for`)
- **Vanilla CSS with design tokens** — no Tailwind, shared `--accent-*` / `--gray-*` / `--space-*` custom properties

## Premises

1. **Auth, role-aware access, ownership, and data flow are the graded competencies — and so is CRUD**, per the Problem Statement above. This is no longer an open question (see Resolved Decisions).
2. **A polished 4-feature demo beats a half-working 6-feature demo.** Cut scope, not corners.
3. **The architecture doc is a presentation asset.** Even a minimal creator studio shows architectural maturity if the DI pattern is followed consistently.
4. **The DI abstraction layer is worth keeping** — it's a 2-hour setup cost and a talking point in the defense ("swap mock for real backend via DI token, zero feature code changes"). To make that claim true rather than mostly-true, it needs to be applied to **every** data-backed feature, Wishlist included (see Resolved Decisions).
5. **Vanilla CSS with design tokens** — the token system is already defined, zero dependencies, and avoids the Tailwind learning tax under time pressure.

## Resolved Decisions (Council Review)

These are direct responses to the Council Verdict's findings, in the order the council raised them.

### 1. CRUD ruling (Open Question #1, resolved)

The Problem Statement at the top of this document already answers this: the grading panel evaluates "auth, role-aware access, ownership checks, **CRUD**, and data flow." CRUD was never actually undecided — it was written into the brief and then contradicted by treating Creator Studio (the only CRUD surface in the app) as a stretch goal. That contradiction is fixed here.

**Decision:** Creator Studio (Task 9) is promoted from *stretch goal* to **committed scope, minimal version** — create + edit only, using the same `GameFormComponent` for both, plus the soft-delete action already specified. No listing-table polish beyond a plain `<table>`. It moves out of "Day 9/10 if time permits" and into the main build sequence, targeted for completion by Day 7–8, before final polish. See the updated [Build Order](#build-order-task-by-task) below.

### 2. `test-suite-plan.md` status

**Decision:** `test-suite-plan.md` is explicitly downgraded to *aspirational / post-capstone reference material*. It is not a build requirement for this project. The Jest/Cucumber+Playwright/Playwright-E2E/Stryker/CI stack it describes is a reasonable target for a team with months and a deploy target — not for a solo student with 10 days and a project that "runs locally via `ng serve`" (see Distribution Plan). The **only** testing commitment for this capstone is Task 10.1 below: unit tests for `DownloadButtonComponent`'s state transitions and the three route guards. If time allows beyond that, pull individual test cases from `test-suite-plan.md`'s Section 2 (Jest specs) — never its BDD/E2E/mutation layers, which are out of scope entirely.

### 3. Wishlist DI gap

The council correctly flagged that Wishlist is the one routed, guarded, nav-linked feature with no model, no service interface, and no DI token — a direct violation of the DI-abstraction principle this project is built to demonstrate (`explanation-di-abstraction.md`).

**Decision:** Close the gap rather than special-case it away — it's a small addition, and leaving it open undermines the "every feature codes against an interface" claim in a live defense. Concretely:
- Add a `WishlistEntry` model (`id`, `userId`, `gameId`, `addedAt`) to `core/models/`.
- Add a `WISHLIST_DATA` injection token and `WishlistDataService` interface (`getWishlist(userId)`, `addToWishlist(userId, gameId)`, `removeFromWishlist(userId, gameId)`) alongside the other three tokens in `core/data/tokens.ts`.
- Implement `MockWishlistDataService` the same way as the other mock services (in-memory array + `LocalStoreService` persistence).
- `WishlistComponent` injects `WISHLIST_DATA`, not a raw `LocalStoreService` call.

This is a Task 1.6 / Task 6 addition, folded into the existing build order below rather than a separate milestone.

### 4. "Quick acquisition" from Wishlist has no wiring path

The council's Outsider is right that `GameCardComponent`'s documented outputs (`select`, `toggleWishlist`) don't support a "buy/download directly from the wishlist card" interaction implied by TODOS.md 6.3.

**Decision:** Simplify. "Quick acquisition" means: clicking a wishlist card's cover/title (the existing `select` output) navigates to `/games/:id`, where the normal 5-state `DownloadButtonComponent` handles acquisition. There is no separate in-card download action on Wishlist. This removes an unspecified feature rather than inventing new component contracts under time pressure.

### 5. Orders "out of scope" comment

`frontend-architecture.md`'s folder-structure comment marking `orders/` as "stubbed — out of scope" is a stale annotation left over from an earlier draft and is superseded by every other reference in that same document (route table, page-flow diagram, data model, milestone table) plus this document's Task 6.4. Orders is implemented, required. That file's comment should be corrected the next time `frontend-architecture.md` is revised; noting it here so it isn't silently trusted in the meantime.

### 6. Items noted but deliberately not fixed in this revision

Kept out of scope for this document, flagged so they aren't lost:
- `site_architecture.md`'s `stateDiagram-v2` for the download button is missing the Anonymous → Owned transition (a returning user who already owns the game and gets bounced through login) that its own flowchart allows. Needs a fix in that file.
- Route/component counts in `README.md` ("16-route table", "21 components") don't match the actual tables in `site_architecture.md` (18 rows) and `pages_components_map.md` (25 rows). Cosmetic, fix opportunistically, not a build blocker.
- No restore path exists anywhere in the spec for a soft-deleted game (`deletedAt` is never unset by any guard/route/service). This is accepted as intentionally out of scope for the capstone — not a bug, just not a feature — rather than something to build under time pressure.
- `TODOS.md`'s "Agent Execution & Quality Workflow" section references ~20 named tool/skill hooks (`tdd-workflow`, `delivery-gate`, `hookify-rules`, `canary`, `retro`, etc.) that are undefined anywhere in this doc set. Treat that entire section as optional/best-effort, contingent on whatever tooling is actually available in the build environment — not a hard requirement of this plan.

## Approaches Considered

### Approach A: Full Architecture
Build all 5 milestones as written. High risk of incomplete features at demo time for a solo developer in 10 working days.

### Approach B: Milestone Triage (CHOSEN, revised)
Build M1 (auth), M2 (catalog + game detail), M4 (library + download), **and a minimal M3 (creator studio: create + edit only)**, with the DI abstraction layer applied consistently across all data-backed features including Wishlist. Ship polished, fully working, over an aspirational-but-unbuilt test pyramid.

### Approach C: Parallel Sprint
Designed for 3-person parallelism. Not viable because the team structure is effectively solo.

## Recommended Approach

**Approach B: Milestone Triage (revised)** — ship the 4 features that demonstrate the graded competencies, including a minimal but real CRUD surface, polished and working. The gated download flow (your "coolest part") still gets the most attention and the most testing effort. Creator Studio is committed but deliberately minimal — no listing-table polish, no advanced validation UX beyond the documented rules — so it doesn't crowd out the download flow's polish time.

## Mid-Build Change & Feature Strategy (3-Tier Rule)

To protect the 10-day capstone deadline while enabling creative iteration:
- **Tier 1 (Core Fixes — Do Immediately)**: Any fix directly impacting Auth, Catalog, Guards, the Gated Download flow, or the minimal Creator Studio CRUD path is addressed immediately.
- **Tier 2 (Micro-Polish < 30 min — Build Inline)**: Small UI wins (e.g. badge styling, smooth tag chip transitions, toast alerts) can be built directly.
- **Tier 3 (Structural Features > 1 hr — Log to TODOS.md)**: Features like user reviews, game price sorting, or creator analytics are logged to `TODOS.md` and tackled only on Day 9/10 if core milestones are complete.

**Kill-switch (new):** If Day 8 arrives and any of Auth, Catalog/Detail, Gated Download, or minimal Creator Studio CRUD is not functionally complete, all Tier 2 and Tier 3 work stops — including further documentation polish — and every remaining hour goes to finishing the incomplete Tier 1 milestone. Documentation and the Task 10 unit tests are the first things cut if the schedule slips; a working demo of the five graded competencies outranks a complete doc set or a green test suite.

## Build Order (Task-by-Task)

### Phase 1: Foundation (M0 + M1)

**Task 1: Scaffold + Core Layer**
- `ng new nexora --standalone`
- Set up folder structure: `core/`, `shared/`, `features/`, `layout/`
- Create design tokens in `styles.css` (section 13 of architecture doc)
- Create `core/models/` — all TypeScript interfaces (`User`, `Game`, `LibraryEntry`, `Order`, **`WishlistEntry`**) with the `roles` array and `deletedAt` field from grill-me decisions
- Create `core/persistence/local-store.service.ts` — IndexedDB wrapper
- Create `core/data/tokens.ts` — DI injection tokens (`GAMES_DATA`, `LIBRARY_DATA`, `USERS_DATA`, `ORDERS_DATA`, **`WISHLIST_DATA`**)

**Task 2: Auth + Seed Data**
- Create `core/auth/auth.service.ts` — signals-based session state
- Create `core/auth/auth.mock.ts` — fake login matching email against seeded users and simulated 1-click social sign-in (Google & Apple)
- Create `core/auth/auth.guard.ts` — with `returnUrl` support
- Create `core/auth/role.guard.ts` — checks `roles.includes('creator')`, redirects to `/catalog`
- Create `features/auth/` — login, register, and forgot-password pages with email/password form, "I want to publish games" toggle, demo account pills, and **Google & Apple social login buttons using crisp inline SVG icons (zero PNG dependencies)**
- Seed data: 3 users, 10 games (6 free, 4 paid), 2–3 LibraryEntries, 1 Order
- Place sample package files in `src/assets/sample-packages/`

### Phase 2: Public Features (M2)

**Task 3: Catalog & Genre Directory**
- Create `core/data/games/games-data.interface.ts` and `games-data.mock.ts`
- Create `features/game-catalog/` — grid layout, tag filter chips (dynamic vocabulary), search input
- Create `features/genres/` — visual genre directory aggregating unique tags with live counts
- Create `shared/ui/game-card/` — cover image, title, price badge, wishlist toggle
- Create `shared/ui/loading-spinner/`
- Catalog page: CSS Grid, responsive (1 col < 768px, multi-col ≥ 768px)

**Task 4: Game Detail + Creator Profile + Layout + 404 + Support**
- Create `features/game-detail/` — hero cover, 2-column layout (info left, actions right), creator link, screenshot row
- Create `features/creator-profile/` — creator storefront, avatar, bio, badge, published games grid
- Create `features/not-found/` — 404 page for broken links and invalid game IDs (`**` wildcard route)
- Create `features/support/` — Help & Support Center with FAQ accordion, reactive contact/ticket form, and Privacy & Data Trust Notice card (`#privacy`)
- Create `layout/header/` — conditional nav (anonymous: Catalog + Genres + Login; buyer: + Library + Wishlist + Orders + Profile; creator: + Creator Studio), display name + logout, hamburger at mobile
- Create `layout/footer/` — copyright and footer nav links (Catalog, Support, Privacy → `/support#privacy`)
- Create `core/data/users/users-data.interface.ts` and `users-data.mock.ts` — for resolving ownerId → displayName
- Hook up routing in `app.routes.ts`

### Phase 3: Gated Features (M4)

**Task 5: Download Button + Purchase Flow**
- Create `shared/ui/download-button/` — the 5-state component (anonymous → "Download", free+unowned → "Download Free", paid+unowned → "Buy $X.XX", owned → "Download", deleted → "Unavailable")
- Create `shared/ui/purchase-confirm-modal/` — game title + price + Confirm/Cancel
- Create `core/data/orders/orders-data.mock.ts`
- Wire download-button into game-detail page

**Task 6: Library, Wishlist, Orders & Profile**
- Create `core/data/library/library-data.interface.ts` and `library-data.mock.ts`
- Create `core/data/wishlist/wishlist-data.interface.ts` and `wishlist-data.mock.ts` — **same DI pattern as Library/Orders (see Resolved Decisions #3)**
- Create `features/library/` — list of owned games with Download button, disabled for soft-deleted games
- Create `features/wishlist/` — bookmarked games grid; clicking a card navigates to `/games/:id` (see Resolved Decisions #4 — no separate in-card acquisition action)
- Create `features/orders/` — order history receipts table
- Create `features/profile/` — user settings, role pills, and demo database reset button
- Wire the full download chain: auth gate → free/paid branch → order creation (if paid) → library entry → file download
- Test the complete anonymous → login → returnUrl → download flow

**Task 7: Integration + Bug Fixes**
- Test all flows end-to-end: anonymous browsing, login, download free game, purchase paid game, view library, re-download, logout/login as different user
- Fix layout bugs, responsive issues, loading states
- Add `shared/ui/empty-state/` component for empty library, no search results, empty wishlist

### Phase 3.5: Creator Studio — Committed, Minimal Scope (formerly Task 9 stretch goal)

**Task 8: Creator Studio & Game Publishing (required — CRUD)**
- Create `features/creator-studio/` — game list table (title, price, date, Edit/Delete). Plain `<table>`, no extra polish.
- Create game form (reused for create and edit) — with tag chip input, validation
- Create `core/auth/ownership.guard.ts`
- Wire up `/studio`, `/studio/games/new`, and `/studio/games/:id/edit` routes per the [route table](docs/reference-routes-guards.md#route-table)

> Target: complete by Day 7–8. If the kill-switch above triggers before this is done, ship with Create + Delete only and drop Edit — Create + soft-Delete still demonstrates two-thirds of CRUD plus the ownership guard, which is enough to defend live.

### Phase 4: Polish (M5)

**Task 9 (renumbered from 8): Error States + Edge Cases**
- Add `?simulateErrors=true` query param support
- Ensure error states render correctly (loading-spinner, empty-state, error messages)
- Test returnUrl edge case (buyer → login → returnUrl to /studio → roleGuard redirects to /catalog)

**Task 10: Final Polish + Presentation Prep**
- Review and clean up code
- Write unit tests for `download-button` (free/paid branching) and auth guards — **this is the entire required testing scope; do not pull in `test-suite-plan.md`'s BDD/E2E/mutation layers (see Resolved Decisions #2)**
- Prepare demo script: walk through each flow for the grading panel
- Ensure seed data looks good (plausible game titles, picsum.photos images)
